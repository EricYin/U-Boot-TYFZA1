# 网页上传速度审查

用户报告的是 U-Boot 恢复网页上传固件约 1 MB/s。这个数值约等于 8 Mb/s，不能单独证明网口协商速度。片内 PHY 驱动支持 10/100/1000 自动协商；MAC 使用实际速率和双工设置。新版页面从正在使用的 PHY 显示实际链路速度。

## 确认的队列与窗口不匹配

固定 Realtek 驱动 `eth_ni.h` 的 RX_BASE_ADDR=0、RX_TOP_ADDR=0x2ff，硬件接收 XRAM 总共 6144 字节。每个满长以太网帧还要占用 XRAM 头部和对齐空间，队列只能容纳约三个满长帧。RX 是 CPU 逐字读取 XRAM，再经 lwIP 拷贝入上传 RAM；不是 Linux 的 DMA 加速路径。

旧配置继承 `CONFIG_LWIP_TCP_WND=3000000`、接收 scale=7，允许发送端向这个轮询收包设备突发大量数据。上传回调正常消费 RAM 数据并更新 TCP 窗口；未发现 1 MB/s 的应用限速，也未发现每个上传包固定睡眠。NAND 擦写发生在上传完成后，不能解释纯上传阶段的速度。

修订把接收窗口设为 2920（两个 1460-byte TCP 段），接收 scale=0，给控制报文留出接收队列空间。发送窗口和网口自动协商保持原设置。它约束单个合规 TCP 上传的在途数据，不是对多客户端并发或广播洪泛的保证；大 RTT 网络下小窗口会限制吞吐，恢复页面的目标是本地直连维护。

## 可重复的离线证据

`test_tcp_upload.py` 编译项目实际固定的 lwIP TCP/IP 源码与生成的 lwipopts，读入实际构建的接收窗口和 RX 队列大小。测试把 CPU 暂停期间收到的突发排入有限队列，再把保留的 IP/TCP 包交给真实 `ip4_input` / `tcp_recved` / `tcp_output`，检查数据消费和 ACK 推进。

- 旧窗口：10 个满长段的突发中，队列丢 7 个；消费 4380 字节，ACK=2921。
- 新窗口：100 轮两段突发，共 200 段、292000 字节，无溢出；ACK=292001，无需等待定时器才能继续。

这个压力模型证明了旧窗口允许突发溢出、新窗口在同一场景中消除了它。模型没有测量真实 CPU 收包速度、线缆、对端网卡或网友当时的丢包情况，不能独立认定其历史 1 MB/s 的全部根因，也不构成新版实机吞吐成绩。

本次按要求不刷机、不重启。精确的历史原因和新版 MB/s 仍需 U-Boot 下的协商结果、抓包或测速才能确认；不把离线通过写成实机问题已经完全解决。

# 网页上传速度复核

实机基线为 1.6（`d0cf559`）、TYFZA1 全千兆版与 Mac 有线直连，双方协商 1000 Mbps 全双工。原版上传 12,257,594 字节的 0.8.3-beta 固件到 RAM 用时 14.10 秒，约 0.87 MB/s；CPU XRAM 接收丢包计数增加 1436，发送端报告 1500 个 TCP 重传包。收到的固件 CRC32 为 `49accdd1`，与源文件一致。

同样的 8 MiB 数据在发送端均匀发送时约 11.98 MB/s，XRAM 丢包和 TCP 重传均为零；不限制发送节奏时约 0.90 MB/s，分别有 836 次 XRAM 丢包和 833 个 TCP 重传包。该对照支持突发流量导致接收队列溢出，但不能确定 CPU 收包路径中哪一部分最耗时。

## 接收窗口实验

CPU XRAM 的 RX 环为 6144 字节。TCP 接收窗口表示连接允许的在途数据，并不等于硬件环大小；它也决定了存在 RTT 时的吞吐上限。本次将恢复环境的 `TCP_WND` 从上游默认的 3,000,000 字节调整为 5840 字节（四个 1460 字节 TCP 段），并将接收窗口缩放设为 0，保持窗口通告的字节精度。它限制一次到达的 TCP 突发，不修改 PHY 协商速率。

下表为相同的 8 MiB 数据、1460 字节发送块、`TCP_NODELAY`、发送端不主动限速时的实测。速度和丢包受双方调度及链路影响，不是保证值。

| 接收窗口 | 速度 | XRAM 丢包 | TCP 重传包 |
| --- | ---: | ---: | ---: |
| 3,000,000 字节，原版 | 0.90 MB/s | 836 | 833 |
| 4380 字节 | 16.62 MB/s | 0 | 0 |
| 5840 字节 | 19.27 MB/s | 4 | 8 |
| 7300 字节 | 10.85 MB/s | 574 | 1148 |
| 11680 字节 | 16.66 MB/s | 437 | 823 |

5840 字节窗口的真实固件上传用时 0.638 秒，约 19.21 MB/s，XRAM 丢包 4 次、TCP 重传 8 包，RAM CRC32 仍为 `49accdd1`。另外三次 8 MiB 上传约 19.21–19.30 MB/s，XRAM 丢包为 1–4 次。浏览器使用恢复网页自身的 XHR 上传函数发送 8 MiB 页面生成的数据，用时 0.455 秒，XRAM 丢包 7 次，RAM CRC32 为 `1ad2bc45`。仅将接收帧批量移入软件队列的实验在默认大窗口下仍有 765 次 XRAM 丢包，未采用。

## 适用范围与测试边界

四段窗口在本次直连测试中减少丢包并明显提高上传速度，但不能保证所有发送端和链路无丢包。窗口还会限制高 RTT 下的速度：忽略其他开销，5840 字节除以 3 ms 约为 1.95 MB/s，除以 10 ms 约为 0.58 MB/s。恢复网页通常在本地有线链路使用；对更高延迟场景，应继续研究硬件流控或接收路径，而不是把这次直连结果当作通用最优值。

`tests/test_tcp_upload.py` 使用固定版本的真实 lwIP 与虚拟链路，比较两段、四段和上游窗口在不同 RTT 的窗口影响；模型并不模拟完整的重传或实际设备性能。测试也保留慢 CPU 下四段窗口仍可能丢包的情形。

多窗口对照使用从 RAM 运行、启动早期加入诊断输出的候选。早期无诊断构建从已运行的 U-Boot 直接跳转时两次停在初始化阶段，继电器冷启动恢复了原有 1.6；随后另一份包含相同网络修改、无启动诊断的提交构建成功从 RAM 启动，真实固件上传用时 0.645 秒，约 18.99 MB/s，XRAM 丢包 2 次、TCP 重传 4 包，RAM CRC32 一致。最终可刷写包尚未实际刷入或验证冷启动，不能把 RAM 实验等同于冷启动验证。完整实测数据保存在本次工作区的 `artifacts/uboot-upload-fix-20261030/`。

# 网页上传速度复核

本地 1.6 的 b8d6462 修订曾把 TCP 接收窗口缩到 2920 字节。这会造成明确的吞吐回归，本次撤回该调整，恢复固定上游默认 `CONFIG_LWIP_TCP_WND=3000000`、接收 scale=7。没有引入新的“最优窗口”猜测，也没有改 PHY 协商速率。

## 为什么不能按硬件 FIFO 大小设置 TCP 窗口

片内 NI 接收 XRAM 确实只有 6144 字节，满长帧加头部、对齐及环形队列空位后大约可同时容纳三个包。但 TCP 窗口表示连接可以接收的在途字节，数据还会被 CPU 持续搬入软件缓冲并交给 HTTP 上传 RAM。它不等于某一瞬间必须同时存在于硬件 FIFO 的数据。

前一版测试暂停 CPU，再把整个突发塞入 FIFO，所以“大窗口丢 7 包、小窗口无丢包”只说明那个设定下的队列容量，不能证明设备实际溢出，更不能证明窗口小就是最佳修复。这个旧证据不再作为上传低速根因或性能改善依据。

## 2920 字节窗口的确定性代价

忽略其他开销时，吞吐上限约为窗口 / RTT：

| RTT | 2920 字节窗口的理论上限 |
| --- | --- |
| 0.1 ms | 29.2 MB/s |
| 1 ms | 2.92 MB/s |
| 3 ms | 0.97 MB/s |
| 10 ms | 0.292 MB/s |

实际 lwIP 的窗口更新阈值还会随窗口缩小。本次真实 TCP/IP 栈用例中，同样接收 200 个满长段，2920 配置发送 200 个 ACK，原配置发送 100 个；每包 ACK 增加 CPU 与 XRAM TX 的工作量。

## 新的测试与边界

`test_tcp_upload.py` 编译项目固定版本的真实 lwIP，读取生成的窗口、scale 和 XRAM 配置，用虚拟时钟模拟链路序列化、RTT、CPU 持续收包及有限 FIFO。发送端遵守实际 ACK/窗口，固定十段拥塞窗口以隔离接收窗口影响。测试覆盖 0.1/1/3/10 ms RTT、快速和慢速 CPU。它不是完整拥塞控制或重传模拟，出现丢包即记录停止。

在假定每帧处理 2 us、RTT 3 ms 的模型中，两种配置都无 FIFO 丢包，2920 窗口约 0.97 MB/s，默认窗口约 4.94 MB/s；默认窗口此时受模拟发送端的十段拥塞窗口限制。这些数字仅用于说明因果，不是 Taurus 实测成绩。在假定每帧处理 100 us 时，大窗口仍可能溢出；保留这个失败场景，避免用测试宣称已解决硬件处理速度不足。

用户历史报告的网页上传约 1 MB/s 根因仍未确认。源码未见固定 1 MB/s 限速或每包睡眠；普通上传写入 RAM，NAND 写入在上传结束后。CPU 搬运、网络 RTT、对端、真实协商和丢包都可能影响速度。本次没有刷机、重启或实机测速，不宣称恢复默认窗口已经修复历史低速。

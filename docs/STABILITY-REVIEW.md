# 日常使用稳定性复核

基线：本地 1.6 / 0b5911b。无实机访问、刷写、重启或 GitHub 推送。

## 已确认并修复

1. **上传可覆盖运行栈。** `upload_region_valid` 将 `gd->start_addr_sp` 直接用作上传结束上限。但 ARM 栈向低地址增长，固定上游 `lmb_reserve_uboot_region` 明确从 `start_addr_sp - CONFIG_STACK_SIZE` 开始保留内存。本构建 CONFIG_STACK_SIZE 为 16 MiB。原判断可能接受侵入栈保留区域的大文件或自定义 loadaddr，破坏正在执行的 HTTP/Flash 调用栈。现与现有 LMB 保留规则一致，结束地址超过栈底即拒绝，并检查减法下溢。没有修改栈大小或常规上传地址。

2. **网口启动失败被上层旧状态覆盖。** `eth_init` 调用 `eth_start_udev` 后，失败时用仅记录 DM 探测结果的 `eth_errno` 覆盖返回值。probe 成功而 PHY/start 失败时，该值可以是 0；网络封装便误认为启动成功，继续增加网络使用计数，后续重试与清理走错分支。现保留本次 start 的实际返回值。反向用例复现 -EIO 被改成 0；新增测试连接实际 eth_init 和 net_lwip_eth_start/stop，连续一百次失败后引用计数仍为 0，再成功启动和停止可回到 0。

3. **失败启动后网页轮询不恢复。** 前端 monitor 在 rebooting 为真时直接 return，没有安排下一次轮询。一旦轮询恰好发生于启动期间，后续启动校验失败虽然清除 rebooting，自动状态和链路更新也不会再运行。现只暂停请求，定时链继续；失败后会继续查询。启动进行中不向设备发轮询请求。

## 验证方式

`test_runtime_boundaries.py` 执行生产上传边界、eth_init 和网络启动/停止包装函数，覆盖正常上传、边界内外、整数溢出、缺少栈空间、失败码传递和反复重试。硬件及全局内存布局由受控模型提供，不访问机器网络。

`frontend_test.js` 执行真实页面脚本，模拟轮询恰好遇到 rebooting，然后解除失败状态，检查计时器和查询恢复。此前两类代码的失败复现记录保留在本地 artifacts。

完整构建和既有启动、PHY、传输、FIP、FIT、签名与恢复用例继续检查。正常系统镜像和恢复分块仍在有效范围内，TCP 窗口和 PHY 时序不变。

## 边界

此次修复针对已确认的软件路径；不承诺零缺陷，不替代设备冷启动、真实协商、掉电恢复及吞吐测量。没有把未测量的历史约 1 MB/s 归因于这些问题。

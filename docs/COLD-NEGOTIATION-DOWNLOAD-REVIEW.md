# 冷启动、协商与网页传输复核

基线：本地 1.6 / 3ed59a0。没有连接或重启设备，没有写 Flash 或推送 GitHub。

## 确认的错误路径

1. **NI 复位超时仍继续初始化。** `cortina_ni_reset` 原来返回 void，等待 init_done 超时只打印消息，仍选通 MAC；probe 继续分配 MDIO 并报告成功。改为返回实际错误，超时不选通 MAC，probe 向上返回失败。原等待上限不变，不增加重试层。
2. **PHY 配置失败被吞掉。** 固定通用 PHY 实现 `genphy_config` 忽略 `genphy_config_aneg` 返回值。写 advertisement、千兆能力或 BMCR 失败时，上层单端口停用分支收不到失败。改为传递原始返回值。
3. **PHY 读取错误被当作协商能力。** `genphy_parse_link` 对 BMSR、千兆本端/对端能力、10/100 能力、扩展状态及强制模式 BMCR 的错误处理不完整，负值可能参与位运算，仍返回成功。现在在位运算前返回读取错误，正常的 10/100/1000 和双工选择逻辑不变。内部 OCP MMIO 本身目前直接返回寄存器值，本次不推测其硬件超时行为；故障注入证明的是软件错误契约，而不是已在样机测得这些错误。
4. **下载中断被误记为完成。** 应用用 fs_file.index 判断是否已读完；HTTP 流可预读到文件末尾而尚有数据等待发送或 ACK。此时 TCP RST、HTTP 超时或服务退出释放连接，可能留下“完成/等待下段”的状态，导致分段下载会话继续占用。现在错误回调和未完成的关闭路径会在释放自定义文件前清除完成标志。正常 ACK 完成仍沿用原路径，正常中间段继续保留会话；上传 RST 的清理修复继续保留。

这些路径都有新测试或明确的生产代码调用链证据。修复前，复位/配置用例失败、协商读取错误用例失败、下载预读后 RST 用例失败；修复后通过。并不表示用户设备已经实测遇到过这些错误。

## 实际执行的验证

- `test_cold_network.py` 编译生产 NI reset 与 genphy_config，注入超时/失败，检查失败返回、MAC 选择与 probe 调用顺序。
- `test_phy_negotiation.py` 执行真实通用 PHY 配置、自动协商重启和模式解析，使用本端/对端寄存器模型；覆盖六种速率/双工组合、强制模式以及各阶段读写错误。
- `test_download_abort.py` 串接真实 lwIP 错误/关闭回调和应用文件释放，覆盖预读后 RST、超时、服务退出，以及正常中间段和最后一段。
- `test_download_stream.py` 执行生产下载读取函数，逐字节比较物理偏移、坏块 FF、非零分段偏移、UBI 缓存边界、ECC 可纠正错误、短读和失败。
- 原有上传取消、正常启动脚本、FIT/hash/LZMA、双模板签名和恢复写入用例继续运行。

## 保留的限制

本次仍是离线构建和软件故障复现。冷启动时的真实复位、OCP/PHY 电气时序、线缆协商、Flash 读写时延和网页 MB/s 未测量。TCP 窗口、等待时长及统一内部千兆口方案未调整。历史约 1 MB/s 的完整根因仍未确认。
